# BMS Fault Detection — Rules and Machine Learning

The `member2_ml` module implements the diagnostic-analysis stage of the Intelligent ECU Diagnosis project. It consumes time-stamped BMS measurements generated by the simulator, checks configured measurement limits, identifies unusual time windows, classifies known injected fault patterns, and exports structured JSON for downstream reporting.

**Current scope:** simulated BMS data in CSV format. CAN `.asc`/`.blf` decoding and requirement-based ECU functional PASS/FAIL are planned extensions, not implemented features.

## Processing pipeline

```text
member1_simulator/datasets/{train,test}.csv
                  |
                  v
        Validate input + timestamps
                  |
         +--------+--------+
         |                 |
    Session features   10-second window features
         |                 |
    Random Forest     Isolation Forest
    (known classes)   (anomaly detection)
         |                 |
         +--------+--------+
                  |
       Measurement-limit rules
                  |
                  v
      Evidence + diagnostic JSON
```

The three checks are independent:

| Component | Question answered | Output |
|---|---|---|
| Rules | Did a recorded value cross a configured limit? | Rule violations with values and timestamps |
| Isolation Forest | Is a segment of the recording unlike normal training data? | Anomalous 10-second windows |
| Random Forest | Which learned fault pattern best describes the full session? | Predicted class and uncalibrated class score |

An unusual signal does not necessarily mean that the ECU failed its functional test. A protective shutdown may be the *correct* response to a deliberately injected fault.

## Quick start

All commands below are run from the **repository root**, not from inside `member2_ml/`.

### Install dependencies

```bash
python -m pip install -r requirements.txt
```

### Inspect feature extraction

```bash
python member2_ml/src/bms_pipeline.py features --input member1_simulator/datasets/train.csv --out member2_ml/results/train_session_features.csv
```

### Train the models

```bash
python member2_ml/src/bms_pipeline.py train
```

Training creates the two `.joblib` model artifacts and a `training_summary.json` file in `member2_ml/models/`.

### Evaluate against held-out sessions

```bash
python member2_ml/src/bms_pipeline.py evaluate
```

Evaluation reads `member1_simulator/datasets/test.csv`, checks that its session IDs are different from the training IDs, and writes metrics, per-session predictions and diagnostic reports to `member2_ml/results/`.

### Produce JSON reports

For an entire input file:

```bash
python member2_ml/src/bms_pipeline.py predict --input member1_simulator/datasets/test.csv --out member2_ml/results/diagnoses.json
```

For one BMS session:

```bash
python member2_ml/src/bms_pipeline.py predict --input member1_simulator/datasets/test.csv --session-id F02_R002 --out member2_ml/results/example_undervoltage_diagnosis.json
```

### Run tests

```bash
python -m pytest -q member2_ml/tests
```

## Input format

Each independent execution is identified by `scenario_id`. Rows are ordered by `timestamp_s`, measured in seconds. The current extractor requires these columns:

```csv
scenario_id,timestamp_s,pack_voltage_v,pack_current_a,temperature_c,soc_pct
BMS_001,0,360.0,25.0,30.0,80.0
BMS_001,1,359.8,25.2,30.1,79.9
```

The values above are examples, not measured vehicle data. Multiple scenarios may coexist in a single CSV, provided each uses a unique ID.

For **training and evaluation only**, each session must also have one consistent `scenario_fault_id` identifying its injected class (`F00`–`F07`). The generator's additional metadata such as `fault_type`, `fault_detected`, `root_cause`, and `fault_start_time_s` is never used as an input feature for inference.

### Adapting external CSV data

When column names differ but the sensor meaning and units are equivalent, edit `config/input_mapping.example.json` and run:

```bash
python member2_ml/src/normalize_input.py --input path/to/external.csv --mapping member2_ml/config/input_mapping.example.json --out path/to/normalized.csv
```

This utility **renames columns only**; it neither converts units nor decodes CAN messages. New ECU types or materially different battery behavior require suitable features and model retraining/validation.

## Feature engineering

The pipeline generates features at two resolutions:

- **Session features (Random Forest):** one numerical row per complete independent test, with 11 summary statistics per measured signal (minimum, maximum, mean, variability, range, percentiles, changes and step sizes), plus sample count, duration and maximum sample gap. This yields **47 numerical features** for the current four signals.
- **Window features (Isolation Forest):** the same 11 per-signal statistics computed over **10-second windows**. The model identifies unusual windows rather than only returning a whole-session score.

Missing numeric values are handled through the fitted preprocessing pipeline; missing timestamps or duplicate timestamps within a session are rejected. Fault annotations are excluded from predictive features to prevent label leakage.

## Model training and evaluation

### Random Forest: identify known fault patterns

`RandomForestClassifier` is trained on **128 labeled independent sessions** across eight classes: normal, overvoltage, undervoltage, overcurrent, overtemperature, voltage-sensor fault, current-sensor fault, and temperature-sensor fault. The model learns relationships between numerical features and the injected class.

A prediction is a **known-class hypothesis**, not proof of the physical cause. The model cannot reliably identify a fault class absent from its training data.

### Isolation Forest: identify unusual behavior

`IsolationForest` is fitted on windows extracted **only from normal sessions**. A separate subset of normal sessions is reserved for calibrating the anomaly cutoff at the 95th percentile of its normal-window scores. The default report marks a session anomalous when at least two windows exceed the threshold.

This detector recognizes deviations from its learned baseline; it does **not** identify a root cause or evaluate manufacturer test requirements.

### Held-out results

Evaluation on 32 separate sessions from the same synthetic generator produced:

| Measure | Result |
|---|---:|
| Random Forest classification accuracy | 32/32 (100%) |
| Isolation Forest fault-detection precision | 22/22 (100%) |
| Isolation Forest fault-detection recall | 22/28 (78.6%) |

These are **prototype benchmarks, not real-ECU accuracy estimates**. The data is synthetic, the injected patterns are simple, and the test set contains only four sessions for each class. Random Forest class probabilities are not calibrated root-cause probabilities.

## Rule-based measurement checks

`config/rules.json` currently defines four illustrative battery limits:

| Rule | Condition |
|---|---|
| `PACK_OVERVOLTAGE` | `pack_voltage_v > 420 V` |
| `PACK_UNDERVOLTAGE` | `pack_voltage_v < 300 V` |
| `DISCHARGE_OVERCURRENT` | `pack_current_a > 150 A` |
| `PACK_OVERTEMPERATURE` | `temperature_c > 60 °C` |

Violations are recorded with the observed value, signal, timestamp and matching rule. These limits reflect the simulator configuration—not an OEM-approved functional test plan.

## Diagnostic JSON interface

The main prediction artifact is `member2_ml/results/diagnoses.json`. Its fields include:

```json
{
  "schema_version": "1.1",
  "data_source": "synthetic_bms",
  "session_id": "F02_R002",
  "verdict": "NOT_EVALUATED",
  "measurement_limits_status": "LIMIT_VIOLATION",
  "detected_fault": "UNDERVOLTAGE",
  "diagnostic_status": "suspected"
}
```

This excerpt shows the report structure, not the entire report. Actual reports also include `probable_causes`, `anomaly_detection`, `evidence`, `missing_info`, `recommended_test`, `recommended_test_done`, `model_version`, and `ruleset_version`.

**Status semantics:**

- `verdict = NOT_EVALUATED`: a functional ECU PASS/FAIL verdict cannot yet be established, because protective-response signals and test-plan deadlines are unavailable.
- `measurement_limits_status = LIMIT_VIOLATION`: at least one configured measurement threshold was exceeded.
- `detected_fault`: a supported fault hypothesis when the model prediction and evidence meet the implementation's checks; otherwise it may be `null`.
- `diagnostic_status`: reports whether the findings are suspected, uncertain, or no anomaly was detected.

A downstream agent may explain these findings and recommend investigations, but must not turn suspected faults into confirmed root causes or invent measurements.

## Reproducibility and limitations

- The current models have been tested only on data generated by the included simulator.
- The implementation consumes **normalized CSV**, not raw ASC/BLF or physical test-bench measurements.
- Rule checks cover **measured limits**, not ECU actuator responses, temporal deadlines or full EOL acceptance criteria.
- `*.joblib` files are intentionally ignored by Git; regenerate them with `train`, or distribute them as versioned, trusted artifacts. Loading untrusted serialized model files is unsafe.
- Additional training sessions, more realistic noise, varying operating regimes and independent hardware validation are required before deployment outside the simulation environment.

For the simulator implementation and dataset-generation settings, see [the Member 1 README](../member1_simulator/README.md).
